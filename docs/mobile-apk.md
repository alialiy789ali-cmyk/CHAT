# بناء تطبيق Android (APK) · Building the Android APK

الجوال في هذا المستودع مشروع **Expo / React Native** (`apps/mobile`) بلا مجلد `android/` مُلتزم به —
المجلد الأصلي يُولَّد من `app.json` + `app.config.js` عند البناء. لذلك «نسخة الـAPK» تُنتَج بأحد
الطرق الثلاث أدناه، وكلها تعطي ملفاً واحداً قابلاً للتثبيت.

## أسرع طريق: من GitHub نفسه (بلا حساب Expo ولا أسرار)

> **آخر حزمة مبنية:** [`mobile-arena-fd7cc258-chat-75323dc`](../../releases/tag/mobile-arena-fd7cc258-chat-75323dc)
> — ملف `sovereign-android-75323dc.apk` (٦٧٫٤ ميغابايت) من تشغيل CI رقم `38646257974`. افتح الرابط من
> متصفح الهاتف مباشرة (المستودع عام، ولا يلزم تسجيل دخول).

1. **رابط جاهز بدون أي إعداد:** كل دفعة تلمس `apps/mobile` تبني APK وتنشره تلقائياً كإصدار
   (prerelease) باسم `mobile-<الفرع>-<أول ٧ أحرف من الالتزام>` — اذهب إلى
   [`Releases`](../../releases) ونزّل الملف من متصفح الهاتف مباشرة. أحدث إصدار هو أحدث بناء.
2. **أو تحكّم كامل:** `Actions` ← `Android APK` ← `Run workflow`، واملأ `api_url` بعنوان خادمك
   (مثال: `http://192.168.1.20:8787` أو `https://chat.example.com`) وفعّل `publish_release`.
   إن تركت `api_url` فارغاً يُستخدم متغيّر المستودع `MOBILE_API_URL`، وإن لم يوجد فالعنوان
   الافتراضي `http://10.0.2.2:8787` (عنوان المحاكي، ولا يفيد هاتفاً حقيقياً — لذلك بدّل العنوان
   داخل التطبيق بعد التثبيت، أو أعد التشغيل بالعنوان الصحيح).
3. ثبّت الملف على الهاتف (السماح بالتثبيت من مصادر غير معروفة).

> **ملاحظة تنفيذية مهمة:** تنزيل حِزم Actions (`Artifacts`) يجري من مضيف مستقل عن `github.com`،
> ولا يمكن الوصول إليه من كل بيئة شبكية (وكيل التطوير الذي عمل هنا لا يستطيع)، أما الإصدارات
> فتُخدَم من GitHub نفسه ويُفتح رابطها من متصفح الهاتف بلا تسجيل دخول. لذلك النشر التلقائي كإصدار
> ليس تجميلاً: هو الطريق الوحيد الذي يعمل من أي مكان.

سير العمل يشغّل قبل البناء اختبارات وحدة الجوال (٤٠ فحصاً)، ويتحقق من سياسة الشبكة في المانيفست
المولّد، ثم يقوم بعده بفحص الحزمة: وجود `AndroidManifest.xml` و`classes.dex`، وجود مكتبات
المعالجات، فحص التوقيع بـ`apksigner` (نفس الأداة التي يستخدمها Android)، وقراءة نطاق إصدارات
Android والصلاحيات من الحزمة نفسها بـ`aapt2` وطباعتها في ملخّص التشغيل — لا أرقام مكتوبة تخميناً.

> في التشغيل المحلي داخل بيئة التطوير هذه، جرّبنا البناء على الجهاز وظهر عائق حقيقي: بيئة العمل
> محصورة بالشبكة على `github.com` و`registry.npmjs.org` و`pypi.org`، فلا يمكنها تنزيل توزيعة
> Gradle ولا مكتبات `google()`/`mavenCentral()`، ولا يوجد Android SDK. لذلك البناء يجري على
> مُشغّلات GitHub حيث الشبكة والأدوات كاملة — وهذا مقصود في التصميم لا تحايل.

## طريق Expo السحابي (EAS) — الأفضل للإنتاج

```bash
npm install -g eas-cli
cd apps/mobile
eas login                      # حساب Expo (حساب المالك)
eas build -p android --profile preview      # APK للتوزيع الداخلي (بلا متجر)
eas build -p android --profile production   # AAB للنشر على Google Play
```

ملف `eas.json` في `apps/mobile` يعرّف ثلاث حالات:

| الحالة | الناتج | الاستخدام |
| --- | --- | --- |
| `development` | APK + development client | تطوير مع Metro |
| `preview` | APK، `MOBILE_ALLOW_CLEARTEXT=true` | تجربة على هاتف حقيقي مع خادم LAN بلا شهادة |
| `production` | AAB، `MOBILE_ALLOW_CLEARTEXT=false` | نشر على المتجر (يجب أن يكون الخادم HTTPS) |

`eas` يحفظ keystore ويوقّع البناء، ويمكن تصدير المفاتيح لاحقاً بـ`eas credentials`.

## طريق البناء المحلي (Android SDK على جهازك)

يحتاج: Node 22، JDK 17، Android SDK (Platform 35 + Build-Tools)، واتصال بالشبكة لتنزيل Gradle.

```bash
cd apps/mobile
export EXPO_PUBLIC_API_URL="http://192.168.1.20:8787"    # العنوان المضمّن
export MOBILE_ALLOW_CLEARTEXT=true                        # لخادم http محلي
npx expo prebuild --platform android --clean              # يولّد مجلد android/
cd android && ./gradlew assembleRelease                   # ملف APK في app/build/outputs/apk/release/
```

للتوقيع بمفتاحك أنت (بدل مفتاح التصحيح):

```bash
keytool -genkeypair -v -storetype PKCS12 -keystore sovereign-release.keystore \
  -alias sovereign -keyalg RSA -keysize 4096 -validity 10000
```

ثم أضف إلى `android/app/build.gradle` كتلة `signingConfigs.release` (نفس ما يفعله سير العمل
تلقائياً) وشغّل `./gradlew assembleRelease`. احتفظ بـkeystore ومكانه خارج Git دائمًا: بفقدانه لا
يمكنك إصدار تحديثات لنفس التطبيق، وبالتسريب يمكن لأي أحد إصدار نسخة تحمل هويتك.

## عنوان الخادم: مضمّن عند البناء، ويُغيَّر بعد التثبيت

بنية العناوين في تطبيق الجوال:

1. **عنوان البناء** من `EXPO_PUBLIC_API_URL` (يوضع في `extra.apiUrl` عبر `app.config.js`).
2. **عنوان محفوظ على الجهاز** يكتبه المستخدم في **شاشة الدخول ← «تغيير»**؛ يُقبل `host:port` بلا
   مخطط (يُفترض `http://`)، ويُجرَّب عبر `GET /api/health` **قبل** حفظه، ويُعرض اسم الخادم وإصداره
   عند النجاح (`src/lib/server-address.ts` + `src/lib/api.ts`).

النتيجة العملية: نفس ملف الـAPK يعمل مع خادم LAN اليوم ومع نطاق عليه TLS غداً، بلا إعادة بناء.
هذا يزيل اعتماد التطبيق على عنوان واحد مضمون — وهو أول ما يتغيّر عند النشر الحقيقي.

## `usesCleartextTraffic` — وسبب وجود إضافة إعداد محلية

| `MOBILE_ALLOW_CLEARTEXT` | القيمة في `AndroidManifest.xml` |
| --- | --- |
| غير مضبوط (الافتراضي) | `android:usesCleartextTraffic="false"` — يُرفض أي `http://` ويلزم HTTPS |
| `true` | `"true"` — يُسمح بـ`http://` (خادم LAN بلا شهادة، ومقصود في حالة `preview` فقط) |

**نتيجة تحقق حقيقية أثناء التنفيذ:** مفتاح `android.usesCleartextTraffic` في إعداد Expo **يُتجاهل
تماماً** — لا يوجد في مخطط الإعدادات، و`prebuild` يولّد مانيفست يسمح بالنص الواضح في بناء
`debug` فقط. لذلك نسخة `release` تمنع `http://` بغضّ النظر عن الإعداد، وهذا ما نُفّذ ومُنع... أي أن
الوعد السابق كان سيفشل عند أول تجربة على هاتف مع خادم LAN. الحل المنفَّذ: إضافة إعداد داخل
المستودع — [`plugins/with-cleartext-traffic.js`](../apps/mobile/plugins/with-cleartext-traffic.js) —
تكتب السمة **صراحةً** في الحالتين، وسير العمل يقرأ المانيفست المولّد ويتحقق من مطابقته للسياسة
المطلوبة قبل البناء (`Assert the network policy`)، فلا يمكن للبناء أن ينجح بسياسة مختلفة عمّا طُلب.

`npx expo install expo-build-properties` لم يكن ممكناً هنا (يحتاج شبكة Expo، وبيئة العمل هذه محصورة
بـ`github.com` و`registry.npmjs.org`)، والحل المحلي أفضل للتتبّع: ٤٠ سطراً في المستودع لا تبعية
جديدة، ومُتحقَّق منه محلياً بإنشاء المانيفست مرّتين (بالوضعين).

عند فشل الاختبار مع عنوان `http://` تظهر في الشاشة رسالة تشرح الاحتمالين: شبكة/منفذ، أو حزمة
مبنية بالوضع الآمن (بلا نص واضح).

## ما يعمل بعد التثبيت فعلاً

- تسجيل/دخول حقيقي، محادثات فورية عبر WebSocket، قوائم محادثات وسجل، منشورات وتفاعل.
- **تشفير طرفي حقيقي** (libsignal، مكتبة Signal المرجعية): المفاتيح تُولَّد في الجهاز وتُخزَّن في
  keychain النظام، والرسائل المشفّرة تُقرأ وتُكتب فعلياً — يتحقق منه `npm run test:e2ee:mobile`
  (٣٥ فحصاً مقابل خادم حقيقي) واختبارات وحدة الجوال.
- معاينة الوسائط المحميّة برموز الجلسة (لا روابط عامة).

## ما لا يفعله الـAPK بعد (بصراحة)

- **لا إرفاق ملفات من الجوال**: لا منتقي ملفات في شاشة المحادثة؛ المرفقات المشفّرة منفّذة في الويب.
- **لا شاشة تحقق من الأجهزة** (رقم الأمان) على الجوال — المنطق جاهز ومُختبَر، والشاشة على الويب فقط.
- **لا إشعارات دفع** (FCM/APNs تبعية خارجية) ولا نشر على Google Play (يحتاج حساب المالك).
- **مكالمات الجوال** لم تُختبر بوسائط حقيقية على جهازين.
